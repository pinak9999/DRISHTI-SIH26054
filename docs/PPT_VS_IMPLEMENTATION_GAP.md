# DRISHTI — PPT vs. Implementation Gap Analysis (SIH26054)

**Date:** 2026-10-03  
**Purpose:** Compare presentation-layer claims (PPT targets, demo narratives, documentation framing) against verified implementation reality. Where they conflict, report the discrepancy — do not manipulate the implementation to match the PPT.

> [!CAUTION]
> This document is intentionally uncomfortable. Its purpose is to prevent the team from presenting unverified claims as achievements. Every gap listed here is an honest engineering disclosure, not a failure.

---

## 1. Terminology

| Term | Definition |
|:---|:---|
| **PPT Claim** | A statement from project presentations, documentation, or README that could be interpreted as a capability claim |
| **Code Reality** | What the code actually does, verified by audit |
| **Gap Severity** | `COSMETIC` (wording issue), `MATERIAL` (claim exceeds evidence), `CRITICAL` (claim is factually wrong) |

## 2. Gap Register

### GAP-01: "Physics-Informed" Framing

| Field | Detail |
|:---|:---|
| **PPT Claim** | "Physics-informed expected-value estimation" using "Rotax914-Simplified-Ref-v1.0" |
| **Code Reality** | The reference model uses invented algebraic polynomials (e.g., `CHT_ss = 105.0 + 48.0 * u_load^0.85 + ...`). Only the ISA density formula is from a textbook. No coefficient is derived from Rotax engine data sheets, test-bench measurements, or published thermodynamic research. |
| **Gap Severity** | **MATERIAL** |
| **Recommendation** | Reframe as "simplified analytical reference model inspired by the Rotax 914 class operating envelope." Add explicit disclaimer: "Polynomial coefficients are assumed, not calibrated to engine test data." The existing `ENGINEERING_ASSUMPTIONS.md` already contains this disclosure but it must be propagated to the PPT and README. |

### GAP-02: ML Metrics Presented Without Synthetic-Only Caveat

| Field | Detail |
|:---|:---|
| **PPT Claim** | "Macro-F1 = 0.977", "RUL MAE = 2.805 hours", "Anomaly Recall = 0.888" |
| **Code Reality** | All metrics are computed on synthetic data generated by the project's own fault simulator. The classifier achieves F1 = 1.0 on 7/9 classes because it memorizes deterministic algebraic offsets. |
| **Gap Severity** | **CRITICAL** if presented without caveat; **COSMETIC** if clearly labeled "synthetic-data evaluation" |
| **Recommendation** | Every metric citation must include: "Evaluated on DRISHTI-SynthCorpus-v1.0 (100% synthetic data). These metrics reflect model performance on self-generated deterministic fault patterns and do not constitute evidence of real-engine diagnostic capability." |

### GAP-03: "Nine-Class Fault Classification" Implies Real Fault Data

| Field | Detail |
|:---|:---|
| **PPT Claim** | "9 diagnostic fault classes: Cylinder Overheating, Oil Pressure Drop, Crankshaft Bearing Wear, ..." |
| **Code Reality** | All 9 fault classes are defined by synthetic additive transfer functions with invented magnitudes. No fault signature is derived from real failure-mode data, engine test cells, or published FMEA databases. |
| **Gap Severity** | **MATERIAL** |
| **Recommendation** | Present as "9 representative fault classes with synthetic signatures." Add: "Fault transfer function magnitudes require calibration against real engine failure data before operational deployment." |

### GAP-06: "Digital Twin" Terminology

| Field | Detail |
|:---|:---|
| **PPT Claim** | "AI-Enabled Real-Time Digital Twin" |
| **Code Reality** | The system is a **software demonstrator** with a simplified reference model, synthetic data, and no real-time hardware data stream. A "digital twin" in aerospace typically implies a continuously updated, physics-validated model synchronized with a physical asset. |
| **Gap Severity** | **MATERIAL** (industry terminology) |
| **Recommendation** | Use "digital twin demonstrator" or "digital twin prototype" to distinguish from a production digital twin connected to a physical engine. The existing `ENGINEERING_ASSUMPTIONS.md` header already uses "demonstrator" — this framing should be consistent throughout. |

### GAP-07: "Leak-Free" Pipeline Framing

| Field | Detail |
|:---|:---|
| **PPT Claim** | "Leak-free ML pipeline with engine-level split" |

## 4. What the PPT Should Honestly Say

> DRISHTI is a **software demonstrator** for AI-enabled digital twin health monitoring of aero piston engines. It demonstrates:
>
> 1. A modular architecture for ingesting, validating, and processing multi-sensor engine telemetry.
> 2. A four-value digital twin framework (Actual → Expected → Residual → Predicted) with transparent physics and ML components.
> 3. Deterministic fault simulation and reproducible evaluation across 9 representative fault classes.
> 4. Explainable alert generation and maintenance recommendations.
> 5. Interactive 3D engine visualization synchronized to live telemetry.
>
> **Current limitations:**
> - All training and evaluation data are synthetically generated. ML metrics reflect performance on synthetic patterns, not real-engine generalization.
> - Physics model coefficients are assumed, not calibrated to engine test data.
> - Alert thresholds are demonstrator defaults, not validated operational limits.
> - Validation on real piston-engine telemetry is required before operational deployment.
